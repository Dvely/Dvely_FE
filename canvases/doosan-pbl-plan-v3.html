① 과제 분석 — 우리가 해결해야 할 문제는 무엇인가?

1-1. 핵심 문제

발전소 현장은 고온 배관 구역, 유독 가스 누출 가능 구역, 좁은 철제 계단과 미끄러운 바닥처럼 사람이 들어가기 위험한 구역이 상당수다. 이런 구역일수록 점검 주기가 짧아야 하고, 설비 상태를 알려주는 계기 상당수는 디지털 통신이 불가능한 아날로그 압력계다. 결과적으로 현재 점검은 사람의 눈과 손, 종이 기록에 의존하며 ① 작업자 안전 리스크, ② 점검 데이터의 비정형·비실시간성, ③ 이상 징후 조기 발견 실패로 이어진다.

본 과제는 이 문제를 “사람 대신 4족 보행 로봇을 보내고, 결과를 Digital Twin 관제 화면에서 실시간으로 확인한다”로 해결한다. 실제 로봇 하드웨어를 쓸 수 없으므로 가상 발전소(Virtual Plant)에서 전 과정을 구현·검증한다.

2차로봇솔루션팀실기 투입 전 보행·인식 알고리즘 검증 환경

1-5. 환경 제약과 대응 — 발표 핵심 소재

개발 머신이 macOS(Apple Silicon)라 ROS 2 + 시뮬레이터를 네이티브로 실행할 수 없다. 이 제약을 우회하는 대신 부가 목표로 전환했다.

“과제 요건 충족”에 더해 누구나 docker compose up 한 번으로 재현 가능한 무료 환경을 목표에 추가한다.

이 결정을 계획 단계에서 확정하지 않고, Phase 0에서 실측으로 검증한 뒤 스택을 변경했다. 이 의사결정 기록 자체가 ①의 가장 강력한 발표 재료다.

1-6. 프로젝트 한 문장 정의

우리는 macOS + Docker(arm64 네이티브) 위에서 ROS 2 Jazzy와 Gazebo Harmonic으로 발전소 Digital Twin을 구축하고, 4족 보행 로봇이 험지를 스스로 통과하고(Locomotion), 아날로그 계기와 과열 배관을 눈으로 읽어내며(Inspection AI), 가스 누출원을 추적한 뒤 안전하게 복귀하는(Gas/Safety) 자율 점검 시스템을 개발하여, 그 모든 상태와 결과를 웹 관제 화면에 실시간 시각화한다.

② 문제 분해 — 이 문제를 해결하려면 무엇을 해야 하는가?

2.1 최상위 문제 분해

가상 플랜트 구축 → 이동 능력 확보 → 현장 데이터 해석 → 임무 자율 판단 → Digital Twin 관제 통합

단계대분류해결해야 할 질문
P1Virtual Plant 구축발전소를 어떻게 가상 공간에 재현하고 센서 데이터를 만들 것인가
P2Locomotion (이동 능력)험지에서 넘어지지 않고 목표 지점까지 갈 수 있는가
P3Inspection AI (데이터 해석)로봇의 눈으로 설비 상태를 정량 수치로 바꿀 수 있는가
P4Gas/Safety (임무 자율)스스로 탐색하고 위험 시 스스로 복귀할 수 있는가
P5Digital Twin 통합모든 결과를 하나의 관제 화면에서 실시간으로 볼 수 있는가

2.2 세부 문제 분해

P1. Virtual Plant 구축

  • P1-1 발전소 3D 환경 모델링 (복도 45m × 3.5m × 4m, 공장 25m × 18m × 7m)
  • P1-2 4족 보행 로봇 모델링 (URDF → USD 변환, 관절 drive 설정)
  • P1-3 센서 모델 구성 (LiDAR, Depth, IMU, RGB, 열화상 대체 모델, 가스 센서)
  • P1-4 ROS 2 인터페이스 정의 (토픽·메시지 타입·QoS 계약 확정)

P2. Locomotion Control

  • P2-1 지형 인지: 포인트클라우드 → Elevation Map 생성 및 노이즈 제거
  • P2-2 발 디딤 위치 결정: 평면 분할 → 안전 후보 추출 → 지형 비용 기반 재배치
  • P2-3 MPC 보행 제어기: SRBD 모델링 → QP 정식화 → 예측 구간·가중치 튜닝
  • P2-4 보행 모드 전환: Trot / Crawl 전환 기준 및 전이 로직
  • P2-5 Fall Recovery: 넘어짐 판정 → 기립 시퀀스

P3. Inspection AI

  • P3-1 게이지 검출 및 ROI 정규화
  • P3-2 바늘 각도 산출 → 수치 변환 (목표 오차 5% 이내)
  • P3-3 열화상·RGB 정합 (캘리브레이션 → 시차 보정)
  • P3-4 과열 판정 및 시각화 오버레이

P4. Gas/Safety

  • P4-1 가스 확산·기류 시뮬레이션 환경 구축
  • P4-2 순찰 경로 생성: Viewpoint 비용 설계 → TSP 순서 최적화
  • P4-3 누출원 추적: 농도 구배 추정 → 이동 방향 결정 → 국소 최적 탈출
  • P4-4 자율 복귀: 배터리·통신 트리거 → 장애물 회피 경로 계획

P5. Digital Twin 통합

  • P5-1 모듈 간 통신 구조 설계 (Topic / Service / Action 배분, QoS)
  • P5-2 시간 동기화 및 데이터 정합
  • P5-3 관제 화면 구성 (로봇 상태, 점검 결과, 가스 농도 맵)
  • P5-4 통합 성능 평가 (넘어짐 횟수, 인식 오차율, 지연 시간)

2.3 선후관계

P1 Virtual Plant → P2 Locomotion P1 → P3 Inspection AI P1 → P4 Gas/Safety P2 → P4 (탐색은 이동 전제) P2 · P3 · P4 → P5 Digital Twin 통합
  • P1은 절대 선행: 시뮬레이션 환경 없이는 나머지 모듈 검증이 불가능하다.
  • P2 · P3 · P4는 원칙적으로 병렬. 단 P4는 P2에 실질 의존.
  • P5는 최종 통합이나, 인터페이스 정의(P1-4)는 착수 시점에 확정한다.

2-1. 전체 흐름 (DT 데이터 흐름을 작업 단위로 치환)

개발환경 구축 → Virtual Plant 구축 → Robot Twin(센서·보행) → 인지(Elevation/영상/농도) → 임무 자율화(순찰·추적·복귀) → 데이터 통신 규격 → 관제 시각화 → 통합·검증·문서화

2-2. 의존 관계 그래프

2-3. 선후관계의 근거 (발표 시 강조)

  • P2가 병목이자 인프라: 로봇이 안정적으로 걷지 못하면 점검도 가스 추적도 시작할 수 없다. Module 1은 독립 모듈이 아니라 Module 2·3의 전제조건이라 55h로 가장 크게 배분했다.
  • P1에 ros_gz_bridge가 들어가는 이유: Harmonic은 gz-transport를 쓰므로 센서 데이터가 그대로 ROS 2 토픽으로 오지 않는다. 브리지 설정이 Robot Twin 완성의 일부이며, 이걸 P2로 미루면 Elevation Map 개발이 통째로 막힌다.
  • P3/P4는 병렬 가능: 가스 확산은 시뮬레이터와 무관한 자체 ROS 2 노드(가우시안 플룸)로 구현한다.
  • P5를 따로 뺀 이유: 세 모듈 동시 구동 시의 병목·시간 동기화는 모듈을 다 만든 뒤 대응하면 늦다. 통신 규격은 P3 착수 시점에 초안을 확정하고 P5에서 검증만 한다.

2-4. Module 1 내부의 3단 리스크 분해

MPC는 실패 확률이 가장 높은 항목이라 완주 보장선과 도전선을 분리했다.

단계내용성격실패 시 영향
stage1 champ_tuning기성 4족 보행 스택 + 지형 적응 파라미터 + Trot/Crawl 게이트 전환완주 보장선 — 이 시점에 과제 필수 요건 충족프로젝트 중단
stage2 simple_mpc_pySRBD 모델 기반 간이 MPC를 Python 직접 구현, Prediction Horizon 실험이해도 확보없음
stage3 convex_mpc_cppConvex MPC(MIT Cheetah 방식) C++ 구현도전 · 타임박스 10h없음, 보고서에 시도·한계 기술

Jazzy 전환으로 생긴 stage1의 새 리스크와 이중화

CHAMP는 Humble 기준 스택이라 Jazzy에서 동작한다는 보장이 없다. 완주 보장선이 흔들리면 프로젝트 전체가 흔들리므로 stage1을 이중화했다.

부록 A. ROS 2 통신 구조 설계 초안

요구사항 #9 “통합” 두 질문과 DT-2에 대한 직접 답변. P3 착수 시점에 규격 확정.

A-0. Harmonic 브리지 계층 (v3 신설)

Gazebo Harmonic 센서는 gz-transport 토픽으로 발행되므로 ROS 2 노드가 직접 구독할 수 없다.

[Gazebo Harmonic] gz-transport ├── ros_gz_bridge (LiDAR, IMU, JointState, Clock, cmd_vel) └── ros_gz_image (RGB, Depth, Thermal — 압축 지원) ▼ [ROS 2 Jazzy] 표준 sensor_msgs → 우리 노드들

필요한 토픽만 선별 브리징한다. /clock은 gz→ROS 단방향, 전 노드는 use_sim_time: true.

A-3. 병목·충돌 방지 전략

  1. 브리지 선별 — 필요 토픽만. 이미지는 ros_gz_image 압축.
  2. 대역폭 분리 — 원본 이미지는 로컬만, 대시보드는 CompressedImage + 결과 메시지. rosbridge throttle.
  3. QoS 분리 — 센서 BestEffort, 점검 결과·상태는 Reliable + TransientLocal.
  4. 실행기 분리 — 제어 루프(200Hz)와 비전 추론을 별도 프로세스. 비전은 MultiThreadedExecutor + Reentrant.
  5. 네임스페이스 — 보너스② 대비 처음부터 /robot1/....

A-4. 시간 동기화

  • 전 노드 use_sim_time: true — Gazebo /clock을 단일 시간원. 브리지를 거치므로 Classic보다 더 중요하다.
  • TF2: map → odom → base_link → {lidar_link, rgb_link, thermal_link, gas_sensor_link}
  • RGB + 열화상: 15Hz vs 9Hz → ApproximateTimeSynchronizer 후 Extrinsic
  • 대시보드는 수신 시각이 아니라 stamp 기준 정렬·표시

부록 B. Sim2Real / Sim2Sim 서술

실제 하드웨어 없이, 물리 엔진이 다른 두 시뮬레이터 간 정책 이식(Sim2Sim)을 수행한다. 보너스③에서 Isaac Lab/Genesis(PhysX)로 학습한 PPO를 ONNX로 보내 Gazebo Harmonic에서 실행한다.

차이 요소문제대응
접촉 마찰·강성엔진마다 미끄러짐이 다름마찰계수 0.4~1.2 랜덤화
링크 질량·관성모델링 오차질량 ±15% 랜덤화
액추에이터 지연·토크 한계모터는 즉시 응답하지 않음0~20ms 지연, 토크 포화
센서 노이즈·지연시뮬 관측이 너무 깨끗함IMU/관절각 가우시안 노이즈
관측 정규화 스케일엔진별 단위·좌표 차이ONNX 래퍼에서 입출력 규약 고정
브리지 지연ROS 경로 추론 루프의 추가 지연추론을 전용 노드/플러그인으로 홉 수 최소화

실제 로봇 이관 시 추가 요소: 레그 오도메트리 + IMU EKF, 실시간 커널, E-stop, 센서 캘리브레이션, 설비 도면 기반 3D 스캔. 열화상은 시뮬의 heat signature가 지정 온도를 그대로 렌더링하지만, 실제는 방사율·반사·대기 감쇠가 있으므로 방사율 보정이 추가로 필요하다.
