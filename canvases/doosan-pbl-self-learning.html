1. 도훈 — Locomotion (LI-09 · LI-10 · LI-12)

걷지 못하면 Module 2·3이 시작되지 않는다. CHAMP Jazzy 이식은 불확실하므로, 학습은 “맵을 만들고 → 보행 모드를 고르고 → CHAMP가 안 되면 게이트 생성기로 대체” 순이다. MPC(LI-13)와 Fall Recovery(LI-14)는 P1이라 Phase 2 착수 직전에 붙인다.

LI-09. Elevation Map과 발 디딤점

1. 핵심 개념 라이다·Depth 포인트클라우드를 로봇 발밑의 2.5D 격자(높이맵)로 누적한다. 각 칸은 높이 평균·분산을 들고, 분산이 큰 칸은 발 디딤 후보에서 뺀다. 디딤점은 다리 워크스페이스 안에서 지지다각형이 넓고 모서리·구멍과 떨어진 칸이다.

2. 우리 코드 module1_locomotion/elevation/ · 입력 /lidar/points (PointCloud2), /tf · 출력 /elevation_map (grid_map_msgs), /footholds (PoseArray).

3. 방법 arm64에서 GPU elevation_mapping은 부담이므로 ANYbotics grid_map + elevation_mapping CPU를 1순위. 자체 복셀 높이 히스토그램은 대체 경로. 발 디딤은 높이 기울기 임계 + 발 반지름 팽창으로 단순화한다. 전 칸 A*는 쓰지 않는다.

4. 어려움 시뮬 라이다 이상치가 맵에 남으면 허공에 발을 찍는다. LI-08 필터가 선행이다.

5. 출처

  • ANYbotics/grid_map, github.com/ANYbotics/grid_map — 2.5D 격자 메시지. Jazzy 포크 여부 확인
  • ANYbotics/elevation_mapping, github.com/ANYbotics/elevation_mapping — CPU 모드 파라미터

LI-10. Trot / Crawl 안정성 차이와 전환

1. 핵심 개념 Trot는 대각선 두 발이 동시에 든다. 빠르지만 지지다각형이 순간적으로 선이 되어 험지·계단에서 넘어진다. Crawl(creep)는 세 발이 항상 땅에 있어 느리고 안정적이다. 전환 기준은 높이맵 거칠기(기울기·분산)와 IMU 피치/롤이다.

2. 우리 코드 module1_locomotion/gait/ · 입력 /elevation_map, /imu · 출력 /gait_mode (String: trot|crawl), 게이트 생성기가 이 모드를 구독.

3. 방법 평지·완만한 복도는 Trot, 계단·잔해는 Crawl. 임계는 시뮬에서 넘어짐 횟수로 맞춘다. Pace는 이번 학기 범위 밖.

5. 출처

  • M. Hutter et al., ANYmal 계열 보행 모드 설명 — Trot vs crawling 안정성
  • Raibert, Legged Robots That Balance — 지지다각형과 투영 CoM
  • Unitree Go2 사용자 문서 gait 전환 (Trot/climb) — 실기 용어 대응. 접근일 2026-09-03

LI-12. 자체 게이트 생성기 (stage1-B)

1. 핵심 개념 게이트는 “지금 발 위치 → 다음 디딤점”의 발끝 곡선이다. 사이클로이드·Bezier로 궤적을 만들고, 다리 역기구학(IK)으로 관절각을 푼 뒤 gz_ros2_control에 보낸다. CHAMP(LI-11)가 Jazzy·arm64에서 안 돌 때의 대체 경로가 이 노드다.

2. 우리 코드 module1_locomotion/gait_generator/ · 입력 /footholds, /gait_mode, /joint_states · 출력 /joint_trajectory 또는 position command.

3. 방법 1순위는 CHAMP 포팅(LI-03·LI-11). 실패 판정 기준(빌드 실패, RTF<0.8, 발 미접지)이 나오면 즉시 이 노드로 전환한다. MPC(LI-13)는 품질용 P1이라 게이트 위에 얹는다.

5. 출처

  • ros-controls/gz_ros2_control — Harmonic 관절 명령. github.com/ros-controls/gz_ros2_control
  • Unitree Go2 description (URDF/Xacro) — 다리 IK 링크 길이
  • Di Carlo et al., “Dynamic Locomotion in the MIT Cheetah 3,” ICRA 2018 — 나중에 얹을 Convex MPC의 위치

2. 운학 — Inspection AI (LI-16 · LI-17 · LI-18)

원문 목표는 바늘 오차 ≤5%, 흔들림·저조도, 열화상-RGB 위치 오차 보정이다. 학습 순서는 전처리 → 바늘 각도 → Extrinsic 정합이다. Viewpoint(LI-19)는 태우가 만들고, 운학은 인식 성공/실패를 비용 입력으로 넘긴다.

LI-16. 아날로그 게이지 독해

1. 핵심 개념 원형 압력계는 원 검출 → 바늘 직선 → 영점 눈금 대비 각도 → 눈금 범위로 물리량 환산. OCR은 눈금 숫자 확인용이지 바늘의 주 경로가 아니다. 경량 CNN 키포인트는 오차가 줄 수 있으나 인터뷰에서 “왜 이 방법인가”를 수식으로 답하기 어렵다.

2. 우리 코드 module2_inspection/gauge/ · 입력 /camera/rgb/image · 출력 /gauge/reading (Float32, 단위 bar), /gauge/overlay (Image).

3. 방법 1차 HoughCircles + HoughLinesP (OpenCV). 5%를 못 지키면 바늘 끝 키포인트 네트워크를 보너스로 붙인다. 태우 Viewpoint가 정면·적정거리를 주면 Hough만으로 목표를 맞추는 것이 설계다.

5. 출처

  • OpenCV docs: HoughCircles, HoughLinesP, minAreaRect — docs.opencv.org. 접근일 2026-09-03
  • 게이지 독해 실무: “Analog Gauge Reading” 계열 (원 검출+바늘 각도) 블로그/논문 서베이. 인터뷰용으로 수식(각도→값)을 노트에 고정
  • 과제 원문 #5 Module 2-1: 오차 5% 이내, 흔들림·저조도

6. 동료평가 Module 2-① 전처리 후 바늘·숫자 구분 / 심층: Edge·Hough vs DL 선택 이유

LI-17. 저조도·모션블러 전처리

1. 핵심 개념 발전소 조명은 불균일하다. CLAHE는 타일별 히스토그램으로 국소 대비를 올린다. 보행 진동은 바늘을 호로 번지게 하므로, 짧은 노출 시뮬 + 프레임 스태킹 또는 Wiener/deblur로 바늘 에지를 살린다.

2. 우리 코드 module2_inspection/preprocess/ · 입력 /camera/rgb/image · 출력 /camera/rgb/image_pp. LI-16이 이 토픽만 구독.

3. 방법 CLAHE 필수, deblur는 비용 대비 효과를 P3 초반에 재본다. 조명 엔티티를 Harmonic에서 어둡게 켜 재현한다(수현 월드).

5. 출처

  • Pizer et al., CLAHE (Adaptive Histogram Equalization) — 저조도 대비
  • OpenCV CLAHE, fastNlMeansDenoising — 구현 API
  • 과제 원문 #5 “카메라 흔들림 및 저조도”

6. 동료평가 Module 2-①의 전처리 절 / 심층: 조명 변화 대응

LI-18. 열화상-RGB 정합 (Intrinsic / Extrinsic)

1. 핵심 개념 두 카메라는 위치·화각이 다르다. Intrinsic은 렌즈 왜곡, Extrinsic은 카메라 사이 회전·이동. 평면 가정(배관 벽)이면 Homography로 근사할 수 있으나, 3D 배관은 TF + 투영이 맞다. Harmonic thermal을 별도 링크에 붙이므로 오차가 “시뮬에도 실재”한다. 합성 플러그인 자작은 하지 않는다.

2. 우리 코드 module2_inspection/fusion/ · 입력 /camera/rgb/image_pp, /camera/thermal/image, /tf · 출력 /inspection/thermal_overlay, /thermal_alert.

3. 방법 체커보드로 Intrinsic, 두 카메라 공통 관측점으로 Extrinsic. 운영은 TF2(camera_rgb_optical ← camera_thermal_optical). Homography는 평면 배관 ROI에만.

5. 출처

  • Z. Zhang, “A Flexible New Technique for Camera Calibration,” TPAMI 2000
  • OpenCV calibrateCamera, stereoCalibrate, findHomography
  • Gazebo Harmonic gz-sensors ThermalCameraSensor — gazebosim.org/docs/harmonic, min_temp/max_temp
  • ROS 2 tf2, image_geometry — 광선 투영

6. 동료평가 Module 2-② 위치 오차의 수학적 보정 / 심층: 정합 오차 최소화

3. 태우 — 순찰 경로 · Critical Path (LI-19 × 3)

원문 Module 2-3: “인식이 가장 용이한 위치(Viewpoint)를 경유하는 순찰 경로”. 이것이 P3의 병목이다. 게이지 모델은 운학, 경로 실행은 Nav2(채현 RTH와 토픽만 분리). 태우 산출은 Viewpoint 집합 + 방문 순서 + 충돌 없는 연결이다.

LI-19-A. Viewpoint와 인식 비용함수

1. 핵심 개념 Viewpoint는 게이지·배관을 바라보는 SE(2)/SE(3) 포즈다. 비용은 “그 포즈에서 바늘이 얼마나 잘 읽히는가”의 역수. 항 예시는 ① 게이지 법선과 시선 각 ② 거리(너무 가까우면 잘림, 멀면 해상도 부족) ③ 장애물 가림 ④ 예상 블러(보행 속도). 최소 비용 포즈가 그 설비의 Viewpoint다.

2. 우리 코드 module2_inspection/viewpoint/ · 입력 설비 포즈(/inspect_targets), 맵, 카메라 파라미터 · 출력 /viewpoints (PoseArray). 운학 인식 성공률을 오프라인으로 비용에 넣을 수 있다.

3. 방법 각 게이지 앞 원호 위에 후보를 샘플링하고 비용을 평가. 전공간 최적화는 하지 않는다.

5. 출처

  • Scott, Roth, Rivest 계열 Next-Best-View / inspection viewpoint planning 서베이
  • 과제 원문 #5 Module 2-3, 동료평가 Module 2-③ “인식이 가장 잘 되는 각도와 거리의 가중치”
  • OpenCV projectPoints — 게이지가 이미지에 들어오는 조건

6. 동료평가 Module 2-③ / 심층: Viewpoint 제약 반영

LI-19-B. 방문 순서 — TSP

1. 핵심 개념 Viewpoint가 N개면 방문 순서는 외판원 문제(TSP)다. N이 점검 게이지 수(십여 개)면 완전탐색 또는 2-opt로 충분하다. 거리 행렬은 유클리드가 아니라 A*로 구한 충돌 회피 경로 길이여야 한다. 그렇지 않으면 벽 너머로 직선 연결한다.

2. 우리 코드 module2_inspection/planner/tsp.py · 입력 /viewpoints, 거리 행렬 · 출력 /patrol_order (int[]).

3. 방법 2-opt. OR-Tools는 의존성 대비 N이 작아 이득이 적다. Action /patrol_mission의 goal에 순서 리스트를 넣는다.

5. 출처

  • TSP 2-opt (Croes 1958) — 소규모 점검 포인트
  • 심층 인터뷰 Module 2: TSP, A*를 무엇으로 썼는가

6. 심층 Module 2 순찰 경로 최적화 알고리즘

LI-19-C. Viewpoint 사이 연결 — A*

1. 핵심 개념 격자(또는 Nav2 costmap)에서 A*는 장애물 비용을 넣은 최단 경로를 준다. TSP의 거리 행렬과, 실행 시 경로 추종에 같은 맵을 쓴다. 동적 장애물은 채현 RTH의 Nav2 컨트롤러 몫이고, 태우는 정적 공장·복도 맵을 전제한다.

2. 우리 코드 module2_inspection/planner/astar.py 또는 Nav2 planner 플러그인 · 입력 costmap · 출력 /patrol_path (nav_msgs/Path). 실행 노드는 /patrol_mission Action 서버.

3. 방법 격자 A*를 먼저 구현해 거리 행렬을 채우고, 추후 Nav2 Smac/Navfn에 위임해도 인터페이스는 Path로 고정.

5. 출처

  • Hart, Nilsson, Raphael, “A Formal Basis for the Heuristic Determination of Minimum Cost Paths,” 1968
  • Nav2 docs (Jazzy) planner plugins — docs.nav2.org. 접근일 2026-09-03

4. 수현 — Virtual Plant + 관제 (LI-05 · LI-06 · LI-24)

원문 Digital Twin 4요소 중 Virtual Plant와 Monitoring이 수현 몫이다. 월드가 없으면 전원 정지. 열화상 센서 부착(LI-07)은 환경·비전 경계라 운학과 한 페이지로 맞추고, 수현은 SDF에 heat signature를 넣는 쪽을 맡는다.

LI-05. Harmonic SDF 월드와 제공 에셋

1. 핵심 개념 SDF는 Gazebo 월드·모델 형식이다. URDF는 로봇, SDF는 공장·조명·가스 영역. 최소 크기: 복도 45×3.5×4 m, 공장 25×18×7 m. 방해물 복도 3·공장 5, 로봇 1, 공장기계 1. 제공 패키지(PBL_AssetPackge.zip)는 DAE/STL일 수 있어 Blender에서 스케일·원점·충돌 메쉬를 고친다.

2. 우리 코드 simulation/worlds/plant.sdf, simulation/models/ · launch가 이 월드를 연다.

3. 방법 에셋 변환 → 충돌 단순화(컨벡스) → 복도·공장 연결. Isaac Sim은 Phase 2 이후 금지(실측 스택은 Harmonic).

6. 동료평가 DT-① Virtual Plant가 실제 발전소의 무엇을 반영하는가

LI-06. Go2 URDF와 gz_ros2_control

1. 핵심 개념 Robot Twin은 URDF/Xacro + 센서 프레임이다. gz_ros2_control이 Harmonic 물리와 ROS 2 관절 명령을 잇는다. 카메라 optical frame 규약(_optical, z-forward)을 여기서 고정하지 않으면 운학 정합이 전부 틀린다.

2. 우리 코드 simulation/models/go2/ · 브리지와 함께 ros_gz_sim spawn. 제어는 도훈이 관절 명령을 보냄.

3. 방법 공식 Go2 description을 Jazzy로 포팅(LI-03). 센서는 RGB·thermal·LiDAR·가스 농도를 링크에 부착. thermal은 Harmonic 네이티브.

5. 출처

LI-20. Gaussian Plume 확산

1. 핵심 개념 정상 상태 가우시안 플룸은 풍하 거리 x에서 농도가 횡방향·연직 가우시안으로 퍼진다. C(x,y,z) ∝ Q/u · 1/(σy σz) · exp(−y²/2σy²) · (지면 반사항). σ는 대기안정도(Pasquill-Gifford)로 커진다. 난류는 σ를 키워 국소 구멍을 만든다. 이 구멍이 LI-21의 로컬 최적이다.

2. 우리 코드 module3_gas_safety/plume/ · 파라미터: 누출원 포즈, Q, 바람 벡터 · 출력 /gas/field 또는 로봇 위치에서 샘플한 /gas/concentration (Float32).

3. 방법 닫힌 공장에서는 플룸이 벽에서 잘린다. 단순 반사 또는 영역 마스크. CFD는 범위 밖.

5. 출처

  • Sutton, A Theory of Eddy Diffusion in the Atmosphere / 표준 Gaussian Plume (EPA ISC) 요약
  • Pasquill-Gifford 분산 곡선 — σy(x), σz(x)
  • 과제 원문 #5 Module 3-1 기류·바람 효과

6. 심층 Module 3: 어떤 확산 모델, 실제와의 차이

LI-21. Source Seeking과 국소 최적 탈출

1. 핵심 개념 경사 상승은 농도 구배 ∇C 방향으로 간다. 플룸 구멍에서는 구배가 뒤집혀 가짜 원에 갇힌다. 탈출: 일정 시간 개선 없으면 나선(spiral) 또는 Infotaxis(정보 이득 방향으로 이동). 과제 원문은 “경사 하강법”이라 적혀 있으나 농도를 최대화하므로 구현은 상승이다. 보고서에 용어를 바로잡는다.

2. 우리 코드 module3_gas_safety/seek/ · 입력 /gas/concentration, /odom · 출력 /cmd_vel 또는 Nav2 목표.

3. 방법 1차 유한차분 구배 + 나선 탈출. Infotaxis는 논문 인용용 2차.

5. 출처

  • Vergassola, Villermaux, Shraiman, “Infotaxis as a strategy for searching without gradients,” Nature 2007
  • Olfactory Navigation / source seeking 서베이 (로봇 후각)
  • 과제 원문 #5 Module 3-2, 심층: Local Optima 회피

6. 동료평가 Module 3-① 농도 구배 → 방향 벡터 / 심층 Local Optima

LI-22. 상태 머신과 Return to Home

1. 핵심 개념 임무는 Patrol / Seek / Return / Charge 상태다. 트리거: 배터리 < 20%, 통신 품질 임계. Return은 Nav2로 충전 스테이션 포즈까지 장애물 회피. 태우의 순찰 경로는 중단하고 Seek도 중단한다.

2. 우리 코드 module3_gas_safety/fsm/ · 입력 /battery, /comm_health · 출력 모드, Nav2 NavigateToPose. BT에서 Return이 Seek보다 우선.

3. 방법 Nav2 Behavior Tree에 Recovery·Return 서브트리. 동적 장애물은 DWB/MPPI 컨트롤러. LI-15는 이 노드에서 소비한다.

5. 출처

  • 심층: 자율 복귀 시 동적 장애물

6. 동료평가 Module 3-② 복귀 트리거와 최단 경로 / 심층 동적 장애물
