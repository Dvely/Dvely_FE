케이스명UC-00 웹서비스 운영 자동화 (전체 흐름)
개요비개발자와 입문 개발자가 GitHub 로그인부터 자연어 생성·Docker 미리보기·승인·버전관리·배포·도메인·인프라 운영까지 한 흐름으로 웹서비스를 실제 운영 상태까지 만든다. 사용자는 복잡한 기술 개념 대신 미리보기, 승인 요약, 배포 URL, 현재 버전, 예상 비용만 확인한다.
관련 액터 주 액터 사용자 (비개발자, 입문 개발자)
보조 액터 GitHub, Docker, AWS/GCP, DNS
우선 순위 상 중요도 10
난이도 로그인·프로젝트·Agent 분기·미리보기·승인·배포·도메인·인프라를 하나의 자연어 파이프라인으로 연결할 수 있는 개발 능력.
선행 조건사용자가 GitHub 계정을 보유한다. AWS/GCP 연결과 커스텀 도메인은 필수가 아니다.
후행 조건웹서비스가 배포되어 기본 URL 또는 연결 도메인으로 접근 가능하고, Overview에 Live·현재 버전·최근 이력이 표시된다.
시나리오 기본 시나리오
  1. 사용자가 GitHub OAuth로 로그인한다.
  2. Projects에서 새 프로젝트 생성, ZIP 업로드, 또는 GitHub 레포 불러오기를 한다.
  3. Overview에서 현재 URL, 배포 상태, 버전을 확인한다.
  4. AI Workspace에서 자연어로 생성·수정·배포·도메인·인프라를 요청한다.
  5. 의사결정 Agent가 코드/배포/도메인/인프라 Agent로 라우팅한다. 분기는 사용자에게 보이지 않는다.
  6. 코드 변경은 preview 브랜치에 커밋되고, Docker 미리보기에서 실제 동작을 검증한다.
  7. 승인창에서 한 줄 요약을 확인하고 승인한다. 변경 승인 후에도 즉시 main에 반영하지 않는다.
  8. 배포 요청 시 PR 생성, main/production merge, 버전 증가 후 GitHub Pages 또는 AWS/GCP에 배포한다.
  9. 기본 URL, qeploy.com 서브도메인 또는 커스텀 도메인을 연결한다.
  10. AWS/GCP 프로젝트는 이후에도 자연어로 서버 상태·리소스·비용을 운영한다.
대안 시나리오
A1: 로그인 실패 시
  1. OAuth 취소 또는 state 오류를 안내한다.
  2. 세션을 만들지 않고 재로그인을 유도한다.
A2: 빌드 실패 시
  1. 쉬운 설명, 로그 일부, 수정안 1개를 보여준다.
  2. 사용자가 승인하면 재빌드·미리보기를 진행한다.
A3: 배포 실패 시
  1. 원인과 수정안을 제시한다.
  2. 승인 후 재배포하거나 merge 이력에서 특정 버전으로 롤백한다.
A4: 도메인 중복/사용 불가 시
  1. 승인창을 열지 않고 사용 불가를 안내한다.
  2. 기본 배포 URL로 접근한다.
A5: 클라우드 미연결 시
  1. AWS/GCP 설정을 비활성 표시한다.
  2. GitHub Pages 경로만 사용한다.
비기능적 요구사항성능 : 승인창은 한 줄 요약 중심으로 제공한다.
보안 : 배포·도메인·비용 증가·서비스 영향 작업은 승인 후에만 반영한다. 선택하지 않은 레포에는 접근하지 않는다.
