UC-00 웹서비스 운영 자동화 (전체 흐름)

항목설명
케이스명UC-00 웹서비스 운영 자동화 (전체 흐름)
개요비개발자와 입문 개발자가 GitHub 로그인부터 자연어 생성·Docker 미리보기·승인·버전관리·배포·도메인·인프라 운영까지 한 흐름으로 웹서비스를 실제 운영 상태까지 만든다. 사용자는 복잡한 기술 개념 대신 미리보기, 승인 요약, 배포 URL, 현재 버전, 예상 비용만 확인한다.
관련 액터 주 액터 사용자 (비개발자, 입문 개발자)
보조 액터 GitHub, Docker, AWS/GCP, DNS
우선 순위 상 중요도 10
난이도 로그인·프로젝트·Agent 분기·미리보기·승인·배포·도메인·인프라를 하나의 자연어 파이프라인으로 연결할 수 있는 개발 능력.
선행 조건사용자가 GitHub 계정을 보유한다. AWS/GCP 연결과 커스텀 도메인은 필수가 아니다.
후행 조건웹서비스가 배포되어 기본 URL 또는 연결 도메인으로 접근 가능하고, Overview에 Live·현재 버전·최근 이력이 표시된다.
시나리오 기본 시나리오
  1. 사용자가 GitHub OAuth로 로그인한다.
  2. Projects에서 새 프로젝트 생성, ZIP 업로드, 또는 GitHub 레포 불러오기를 한다.
  3. Overview에서 현재 URL, 배포 상태, 버전을 확인한다.
  4. AI Workspace에서 자연어로 생성·수정·배포·도메인·인프라를 요청한다.
  5. 의사결정 Agent가 코드/배포/도메인/인프라 Agent로 라우팅한다. 분기는 사용자에게 보이지 않는다.
  6. 코드 변경은 preview 브랜치에 커밋되고, Docker 미리보기에서 실제 동작을 검증한다.
  7. 승인창에서 한 줄 요약을 확인하고 승인한다. 변경 승인 후에도 즉시 main에 반영하지 않는다.
  8. 배포 요청 시 PR 생성, main/production merge, 버전 증가 후 GitHub Pages 또는 AWS/GCP에 배포한다.
  9. 기본 URL, qeploy.com 서브도메인 또는 커스텀 도메인을 연결한다.
  10. AWS/GCP 프로젝트는 이후에도 자연어로 서버 상태·리소스·비용을 운영한다.
대안 시나리오
A1: 로그인 실패 시
  1. OAuth 취소 또는 state 오류를 안내한다.
  2. 세션을 만들지 않고 재로그인을 유도한다.
A2: 빌드 실패 시
  1. 쉬운 설명, 로그 일부, 수정안 1개를 보여준다.
  2. 사용자가 승인하면 재빌드·미리보기를 진행한다.
A3: 배포 실패 시
  1. 원인과 수정안을 제시한다.
  2. 승인 후 재배포하거나 merge 이력에서 특정 버전으로 롤백한다.
A4: 도메인 중복/사용 불가 시
  1. 승인창을 열지 않고 사용 불가를 안내한다.
  2. 기본 배포 URL로 접근한다.
A5: 클라우드 미연결 시
  1. AWS/GCP 설정을 비활성 표시한다.
  2. GitHub Pages 경로만 사용한다.
비기능적 요구사항성능 : 승인창은 한 줄 요약 중심으로 제공한다.
보안 : 배포·도메인·비용 증가·서비스 영향 작업은 승인 후에만 반영한다. 선택하지 않은 레포에는 접근하지 않는다.

UC-01 GitHub 로그인

항목설명
케이스명UC-01 GitHub 로그인
개요사용자는 GitHub OAuth로만 서비스에 로그인하고 Projects에서 작업을 시작한다. GitHub 로그인은 필수이며 AWS/GCP 연결은 필수가 아니다.
관련 액터 주 액터 사용자
보조 액터 GitHub
우선 순위 상 중요도 9
난이도 OAuth 인가 코드와 state를 검증하고, 서비스 세션과 GitHub 연동 상태를 분리 저장할 수 있는 개발 능력.
선행 조건사용자가 GitHub 계정을 보유하고 Qeploy 로그인 화면에 진입한 상태이다.
후행 조건서비스 세션이 생성되고 GitHub 연동 상태가 CONNECTED로 저장되며 Projects로 이동한다. 선택하지 않은 레포에는 접근하지 않는다.
시나리오 기본 시나리오
  1. 사용자가 로그인 화면에서 GitHub 로그인을 선택한다.
  2. 시스템이 GitHub OAuth로 이동하고 레포 생성·연결, 브랜치, 커밋, PR, merge, Pages, workflow 권한을 요청한다.
  3. 사용자가 권한을 승인한다.
  4. GitHub가 인가 코드를 반환하고 시스템이 state를 검증한다.
  5. 서비스 세션과 GitHub 연동 상태를 분리 저장한 뒤 Projects로 이동한다.
대안 시나리오
A1: OAuth 취소 시
  1. 로그인 화면으로 돌아간다.
  2. 세션을 만들지 않는다.
A2: state 불일치 또는 토큰 무효 시
  1. 오류를 안내한다.
  2. 재로그인을 유도한다.
비기능적 요구사항성능 : 로그인 시작부터 Projects 진입까지 체감 2초 이내를 목표로 한다.
보안 : OAuth state를 검증한다. 사용자가 생성했거나 명시한 레포에만 권한을 사용한다.

UC-02 프로젝트 관리

항목설명
케이스명UC-02 프로젝트 관리
개요사용자는 Projects에서 목록을 확인하고, 빈 프로젝트 생성·ZIP 업로드·GitHub 레포 불러오기로 프로젝트를 추가한 뒤 Overview로 진입한다.
관련 액터 주 액터 사용자
보조 액터 GitHub
우선 순위 상 중요도 9
난이도 카드형 목록과 생성/ZIP/불러오기 3경로를 제공하고, 프로젝트와 GitHub 레포를 병렬 객체로 관리할 수 있는 개발 능력.
선행 조건사용자가 GitHub로 로그인한 상태이다.
후행 조건프로젝트가 목록에 추가되고 카드에 이름·상태 배지·최근 수정일, Live일 때 URL이 표시된다. 트래픽 분석은 표시하지 않는다.
시나리오 기본 시나리오
  1. 사용자가 Projects에서 목록을 최근 수정순으로 확인한다.
  2. 새 프로젝트 생성, ZIP 업로드, GitHub 레포 불러오기 중 하나를 선택한다.
  3. 빈 프로젝트는 이후 기존 레포 연결 또는 새 레포 생성 후 연결을 선택한다.
  4. 레포 불러오기는 이름만 보고 선택 → 확인 후 목록에 추가한다.
  5. URL은 새 탭, 그 외 카드 클릭은 Overview로 이동한다.
대안 시나리오
A1: ZIP 업로드 후
  1. GitHub 레포 연결이 필요함을 안내한다.
A2: 동일 레포 재불러오기 시
  1. 새 프로젝트로 추가한다.
  2. 휴지통 대화는 자동 복구하지 않는다.
A3: 연결 해제 시
  1. 프로젝트와 레포의 연결만 끊는다.
  2. 레포 삭제는 Danger Zone에서만 처리한다.
비기능적 요구사항성능 : 최근 수정일은 GitHub식 상대시간으로 표기한다.
보안 : 사용자가 명시한 레포만 불러온다.

UC-03 자연어 작업 요청

항목설명
케이스명UC-03 자연어 작업 요청
개요사용자는 AI Workspace에서 자연어만으로 생성·수정·배포·도메인·인프라 작업을 요청한다. 의사결정 Agent가 전문 Agent로 라우팅하며 내부 분기는 보이지 않는다.
관련 액터 주 액터 사용자
보조 액터 GitHub, Docker, AWS/GCP, DNS
우선 순위 상 중요도 10
난이도 자연어 의도를 코드/배포/도메인/인프라로 분류하고, 세션 저장·미리보기·승인창을 한 화면에서 연결할 수 있는 개발 능력.
선행 조건로그인한 사용자가 프로젝트의 AI Workspace에 진입한 상태이다.
후행 조건전문 Agent가 처리하고, 코드 변경 시 preview 커밋과 Docker 미리보기가 준비된다. 사용자는 승인창 한 줄 요약만 확인한다.
시나리오 기본 시나리오
  1. Overview에서 Open AI Agent로 Workspace에 들어간다.
  2. 새 대화 최초 1회 오버레이가 표시되며 화면 클릭 시 닫힌다.
  3. 자연어만 입력한다. 액션 칩은 없다.
  4. 의사결정 Agent가 코드/배포/도메인/인프라 Agent로 라우팅한다.
  5. 필요 시 Docker 미리보기와 승인창을 포함한다.
대안 시나리오
A1: 의도가 불명확할 시
  1. 내부 분기 과정은 노출하지 않는다.
  2. 한 줄로 재질문한다.
A2: 대화 삭제 시
  1. 확인 모달 없이 휴지통으로 이동한다.
  2. 7일 후 완전 삭제되며, 연결 프로젝트가 없으면 복구 불가이다.
비기능적 요구사항성능 : 세션은 최근 수정순이며 제목은 자동 생성된다.
사용성 : 사용자는 미리보기 결과와 승인 요약만 알면 된다.

UC-04 Docker 미리보기

항목설명
케이스명UC-04 Docker 미리보기
개요코드 변경 결과를 Docker 컨테이너에서 실제 설치·빌드·실행하고, 내부 패널에서 클릭·입력 등 실제 사용 테스트를 한다. 단순 정적 렌더링이 아니다.
관련 액터 주 액터 사용자
보조 액터 Docker
우선 순위 상 중요도 9
난이도 컨테이너 안에서 실제 런타임을 구성하고, 미사용 시 종료와 캐시 재사용이 가능한 개발 능력.
선행 조건자연어 요청으로 코드 변경이 발생했거나 미리보기가 필요한 세션이 열려 있다.
후행 조건내부 패널에서 동작을 확인한 뒤 승인 여부를 판단한다. 외부 공개 preview URL은 기본적으로 발급하지 않는다.
시나리오 기본 시나리오
  1. 프로젝트 또는 작업 세션 단위로 컨테이너를 생성한다.
  2. 컨테이너 안에서 설치·빌드·실행한다.
  3. 미리보기 패널에 결과를 표시한다.
  4. 사용자가 클릭·입력·화면 이동으로 테스트한다.
  5. 미사용 시 자동 종료하고 의존성·빌드·이미지 캐시를 재사용한다.
대안 시나리오
A1: 빌드 실패 시
  1. 쉬운 설명, 로그 일부, 수정안 1개를 보여준다.
  2. 단순 실패 메시지만 보여주지 않는다.
A2: 수정안 승인 시
  1. 코드 Agent가 수정한다.
  2. 재빌드·미리보기를 진행한다.
비기능적 요구사항성능 : 반복 작업 시 캐시를 활용해 재빌드 시간을 줄인다.
보안 : 미리보기는 서비스 내부에서만 접근한다.

UC-05 작업 승인

항목설명
케이스명UC-05 작업 승인
개요개발/수정, 배포, 도메인, 인프라 운영은 승인창에서 한 줄 요약을 확인한 뒤 진행한다. 의도 파악 결과는 중간에 노출하지 않는다.
관련 액터 주 액터 사용자
보조 액터 GitHub, AWS/GCP, DNS
우선 순위 상 중요도 10
난이도 승인 대상 4종을 구분하고, Off 시 생략, 도메인 불가 시 창을 열지 않는 분기를 구현할 수 있는 개발 능력.
선행 조건전문 Agent가 작업을 준비했고, 해당 유형 승인이 On이거나 비용·서비스 영향이 있는 작업이다.
후행 조건승인 시 작업이 반영된다. 코드 변경 승인 후에도 즉시 main에 반영하지 않으며 배포는 별도 승인이다. 거부 시 반영하지 않는다.
시나리오 기본 시나리오
  1. 작업 유형에 맞는 승인창을 표시한다. (개발/수정, 배포, 도메인, 인프라)
  2. 배포 승인은 “최신 승인 버전으로 배포할까요?”와 버전·환경·URL·요약을 한 줄로 보여준다.
  3. 사용자가 승인한다.
  4. 개발/수정은 preview에 유지되고, 배포 승인 시에만 PR·merge·버전 증가가 진행된다.
대안 시나리오
A1: 승인 Off 시
  1. 해당 유형의 승인창을 생략할 수 있다.
  2. 비용 증가·서비스 영향 작업은 승인 대상이다.
A2: 도메인 중복/사용 불가 시
  1. 승인창을 열지 않는다.
  2. 사용 불가를 안내한다.
A3: 거부 시
  1. 반영·배포·DNS 변경을 수행하지 않는다.
비기능적 요구사항사용성 : 승인창은 한 줄 요약 중심이다.
보안 : 확인 없이 배포·도메인·인프라 변경이 나가지 않는다.

UC-06 배포

항목설명
케이스명UC-06 배포
개요사용자는 최신 승인 버전 또는 특정 버전을 GitHub Pages 또는 개인 AWS/GCP에 배포한다. 배포 요청 시 PR, merge, 버전 증가, workflow가 진행된다.
관련 액터 주 액터 사용자
보조 액터 GitHub, AWS/GCP
우선 순위 상 중요도 9
난이도 Pages와 AWS/GCP 경로, 버전/롤백, 실패 시 수정안 제시를 하나의 승인 흐름으로 연결할 수 있는 개발 능력.
선행 조건배포할 버전이 미리보기에서 확인되었고 GitHub 레포가 연결되어 있다. AWS/GCP는 계정 연결 시에만 활성이다.
후행 조건Overview에 Live, 현재 버전, 배포 URL이 표시된다. 도메인 미연결 시에도 기본 URL로 접근할 수 있다.
시나리오 기본 시나리오
  1. 자연어 또는 Overview에서 배포를 요청한다.
  2. 승인창에 버전, 환경, 예상 URL, 변경 요약을 표시한다.
  3. 승인 후 PR 생성, main/production merge, 버전 증가가 진행된다.
  4. Pages 또는 AWS/GCP로 workflow를 실행하고 Overview에 URL을 표시한다.
대안 시나리오
A1: 클라우드 미연결 시
  1. AWS/GCP 설정을 비활성 표시한다.
  2. GitHub Pages 경로만 사용한다.
A2: 배포 실패 시
  1. 쉬운 설명, 로그 일부, 수정안 1개를 보여준다.
  2. 승인 후 재배포한다.
A3: 롤백 시
  1. merge 이력에서 특정 버전을 선택한다.
  2. 해당 버전으로 재배포한다.
비기능적 요구사항성능 : 실패 시 원인과 수정안을 함께 제공한다.
추적성 : 버전은 merge 단위로 증가한다.

UC-07 도메인 연결

항목설명
케이스명UC-07 도메인 연결
개요사용자는 기본 배포 URL 외에 qeploy.com 서브도메인 또는 보유 커스텀 도메인을 연결한다. 서브도메인은 랜덤 생성하지 않고 사용자가 이름을 입력한다.
관련 액터 주 액터 사용자
보조 액터 DNS
우선 순위 상 중요도 7
난이도 중복 검사, DNS 확인, HTTPS, 연결 검증을 승인 이후에만 실제 반영할 수 있는 개발 능력.
선행 조건배포되어 기본 URL이 있거나 연결 대상 배포 환경이 선택되어 있다.
후행 조건승인된 도메인으로 접근 가능하고 Overview의 현재 URL이 갱신된다. HTTPS가 적용된다.
시나리오 기본 시나리오
  1. 자연어로 서브도메인 또는 커스텀 도메인 연결을 요청한다. 예: cafe.qeploy.com
  2. 시스템이 중복/사용 가능 여부를 확인한다.
  3. 사용 가능하면 승인창에 도메인, 환경, HTTPS, 예상 결과를 표시한다.
  4. 승인 후 DNS 확인, HTTPS, 연결 검증을 수행하고 Overview URL을 갱신한다.
대안 시나리오
A1: 중복 또는 사용 불가 시
  1. 승인창을 열지 않는다.
  2. 사용 불가를 안내한다.
A2: 도메인 미연결 시
  1. Pages/AWS/GCP 기본 URL로 계속 접근한다.
비기능적 요구사항사용성 : DNS 상세보다 연결 결과와 HTTPS 여부를 확인한다.
보안 : HTTPS 처리와 연결 검증 후에만 현재 URL로 노출한다.

UC-08 인프라 운영

항목설명
케이스명UC-08 인프라 운영
개요AWS/GCP 연결 프로젝트는 한 페이지에서 인프라를 설정하고 예상 요금을 확인한 뒤, 배포 이후에도 자연어로 상태·로그·재시작·리소스·비용 최적화를 요청한다.
관련 액터 주 액터 사용자
보조 액터 AWS/GCP
우선 순위 중 중요도 7
난이도 제공자·리전·리소스·DB 설정과 예상 요금, 승인 대상 운영 작업을 한 흐름으로 제공할 수 있는 개발 능력.
선행 조건개인 AWS 또는 GCP 계정을 연결했다. Pages 전용은 섹션을 숨기지 않고 비활성화한다.
후행 조건선택한 인프라가 반영되고 예상 월 비용이 표시된다. 민감 값은 화면에 그대로 노출하지 않는다.
시나리오 기본 시나리오
  1. 클라우드 연결 후 제공자, 리전, 아키텍처, 리소스, 네트워크, DB를 한 페이지에서 설정한다.
  2. 예상 월 비용·항목별 비용을 표시하고 예산 초과 시 경고한다.
  3. 배포 이후 자연어로 상태, 로그, 장애 분석, 재시작, 리소스, 비용 최적화를 요청한다.
  4. 비용 증가·서비스 영향 작업은 승인창을 표시한다.
대안 시나리오
A1: Pages 전용 시
  1. Cloud·Cost 섹션은 보이되 클릭 불가로 둔다.
A2: Secret 조회 시
  1. Secret은 숨김 처리한다.
  2. 변경 이력만 보여준다.
비기능적 요구사항성능 : 설정 변경 전 예상 요금과 예산 초과 경고를 제공한다.
보안 : Secret은 평문으로 노출하지 않는다. 고위험 작업은 Danger Zone에서만 처리한다.
